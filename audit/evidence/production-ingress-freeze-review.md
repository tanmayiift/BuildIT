# BuildIT ingress freeze and restore — prepared, not executed

Target only `judicious-barracuda-968` in the BuildIT Convex project. This document is a release procedure for root review, not evidence that production has been paused. It does not authorize an unrelated deployment, repository, team, or service.

## Why the existing per-repository switch is insufficient

The old GitHub comment and Autofix paths do not consistently inspect `pausedAt`. Setting repository `enabled=false` is also unsuitable as a temporary release switch: repository synchronization writes `enabled=true` for accessible repositories, and the user-facing restore mutation itself requires enabled repositories. The execution flag is not a general ingress freeze either: Ask and automatic review entry paths do not all check it. Do not change or revoke provider credentials to force a drain.

## Proposed supported control

Convex offers deployment pause/resume in the deployment settings and its administrator API. Pausing blocks new function calls, holds scheduled jobs, and skips cron ticks; source deployment and dashboard edits remain available. This affects all BuildIT app functionality backed by this one deployment for the maintenance window. It does not delete stored data or change repository policies. See [Convex pause behavior](https://docs.convex.dev/production/pause-deployment), [pause API](https://docs.convex.dev/deployment-api/pause-deployment), and [resume API](https://docs.convex.dev/deployment-api/unpause-deployment).

## Exact sequence for root approval

1. Complete builds, required release checks, Vercel authorization, alias/environment verification and the immutable source revision before downtime. Validate `verifyConvexProductionTarget()` against the expected name, type and URL. Preserve both old deployment IDs and the approved commit in the release receipt.
2. Repeat `python3 .local/production-preflight/read-convex.py`. Require complete scans and zero nonterminal paid review/workflow activity, zero in-progress steps, zero work or pending queues in `reviewWorkpool` and `workflow/workpool`, and no pending/in-progress review, Ask, Autofix, or publication scheduler work. Inspect the already-known blocked review separately; do not classify a blocked refusal as an in-flight paid call. If any jobs exist, let them settle under the old code and recheck; never cancel them just to obtain zero counts.
3. Record the freeze UTC timestamp. In the exact production deployment settings, use Pause Deployment and verify its paused state. The equivalent reviewed administrator request is POST `https://judicious-barracuda-968.convex.cloud/api/v1/pause_deployment`; use existing authorized session access in memory, never paste an admin credential or create a new persistent key. Do not send this request until root approves the actual freeze. Confirm a harmless public read is refused. This control is reversible but is a real BuildIT service interruption.
4. After pausing, run `node .local/production-preflight/read-system-queues.mjs`. The built-in `_system/cli/tableData` query via the official CLI’s component-aware `BaseConvexClient` WebSocket path remains available while ordinary functions are paused; this has now been tested on the isolated local backend. Require all 17 administrative table scans to be complete (200-row pages, 20,000-row ceiling with explicit truncation), then inspect their counts and unfinished function names. A pre-pause zero snapshot has a race with a request arriving immediately afterward. If an in-flight paid call cannot be accounted for or administrative evidence cannot rule it out, stop the release and resume the old compatible stack rather than assert a clean drain. Pause does not itself prove that an external provider has completed a request.
5. Deploy and verify the backwards-compatible broker first. Require the intended immutable commit at its production alias. Re-resolve the exact Convex production target, deploy Convex and its additive indexes, then deploy and verify the web alias. Keep the database paused across the API-contract transition. The coordinated script's server guard is read-only authorization; its public page probes must also be checked for compatibility with a paused backend before using one unattended command.
6. Resume only the same deployment, through the original settings page or POST `https://judicious-barracuda-968.convex.cloud/api/v1/unpause_deployment`. If the deployment was already paused before this release, do not resume it automatically. Record the resume timestamp. Verify public reads, both deployment aliases, worker queues, accounting snapshots and telemetry. Reconcile monthly accounting before approving new paid test work.
7. Inspect BuildIT GitHub delivery records for the exact downtime window. Requests can fail before reaching stored webhook records while the database is paused. Do not assume automatic redelivery. Replay only explicitly approved missing BuildIT deliveries after checking replay protection and the US$10 shared spending cap; do not send new comments or trigger unrelated repositories as a shortcut. Restore only controls actually changed by this release, using the saved original state.

## Failure handling

If broker deployment fails before Convex changes, leave the previous Convex/web code intact, verify the original compatible alias, and resume the original database state. If Convex has changed, do not roll workers back across the accounting protocol automatically: preserve compatible broker support and all accounting rows, inspect pending/unknown invocations, and have root choose the recovery revision. Never erase charges, reservations, review evidence or failed delivery records.
